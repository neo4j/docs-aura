[[aura-agent]]
= Aura Agent
:description: This page describes the creation and capabilities of Aura GraphRAG Agent.

label:AuraDB-Free[]
label:AuraDB-Professional[]
label:AuraDB-Business-Critical[]

Aura Agent is a no/low-code agent platform that allows you to build, test, and deploy GraphRAG agents contextualized by your own knowledge graph in AuraDB.

Aura provides the orchestration layer as well as the integration with GenAI models/LLMs and offers different iterative tools that allow your agent to provide the right context to the LLM.

You can test the agent and iterate on it directly in the UI.

Once you are satisfied with your agent, you can either share it internally with other members of your Aura project, or you can make it available externally via either an Aura API endpoint or an MCP server endpoint and thus integrate it into your GenAI application or model.

Internal agents are free to use, but once you make an agent external, it incurs charges per link:https://console.neo4j.io/pricing[Neo4j Aura Pricing].
See also xref:billing/billing-dimensions.adoc[Billing dimensions] for more information on how billing works.

To get started you need a knowledge graph in a running AuraDB instance and you need to make sure *Generative AI assistance* as well as *Aura Agent* are both enabled in the xref:visual-tour/index.adoc#org-settings[Organization settings].
When *Generative AI Assistance* is enabled, *Aura Agent* can be toggled on and off, but if you disable *Generative AI assistance*, *Aura Agent* is automatically disabled.

Additionally, you need to enable *Tool authentication* for the project in which you create the agent.
This is done from *Security* on the organization level.
See xref:security/tool-auth.adoc[Tool authentication with Aura user] for more information.

To create, edit, or delete an agent, you need to be a project admin, project members and viewers can list and use agents but not make any changes to them.

[NOTE]
====
Keep in mind that all Aura agents are located in Belgium, in GCP's `europe-west1` region.
This means that *all* interactions with agents go via Belgium, regardless of whether the agent is internal or external.
====

Aura Agent uses a curated set of AI models to deliver advanced planning, reasoning, retrieval, and explainability.
For more information on how Aura Agent uses AI models, see link:{neo4j-docs-base-uri}/reference/license/agent-ai-model/[License and disclaimers -> How Aura Agent uses AI models].



== Create an agent

Navigate to *Agents* in the left-hand menu and use the *Create Agent* button to start creating your agent.
You can either create an agent from scratch, or use AI to create the agent and generate the tools.

=== Create from scratch

First you select which instance the agent should target.
The instance doesn't have to be running when you configure the agent, but you can't test the agent unless the instance is running.

[.shadow]
.Create an agent from scratch
image::agent.jpg[width=300]

The agent's location (as mentioned in the introduction) is listed but *cannot* be changed.

You need to give the agent a name (it is advisable to use a descriptive name), a description, and optionally prompt instructions.
The more detailed you are in the description and prompt instructions, the better your agent will operate.

You can make the agent externally available right away, but it is recommended to keep it internal while testing it.
You can change the agent's availability at any time.

Then you can start adding the tools that will allow your agent to retrieve specific data from your graph.
Keep in mind that currently the agent only supports *read only* queries against the database.

Once you are satisfied with your agent, use *Create agent* to persist it.

Note also that the conversation history is not currently stored anywhere.

=== Create with AI

If you can describe exactly what your use case is and what you want the agent to do, Neo4j AI can generate an agent for you.
The agent is based on your prompt and the schema of your database.

[.shadow]
.Create an agent with AI
image::create-with-ai.jpg[width=400]

Start by selecting which instance you want to connect to, keep in mind that the instance *must* be running.

If you want your agent to use the <<Similarity Search>> tool, your database needs to have *vector embeddings*.
If it does, select the embedding provider and model for your database.
For more information about vectors and embeddings, see the link:{neo4j-docs-base-uri}/cypher-manual/current/indexes/semantic-indexes/vector-indexes/#embeddings[Cypher Manual -> Vectors and embeddings in Neo4j] and link:{neo4j-docs-base-uri}/cypher-manual/current/indexes/semantic-indexes/vector-indexes/[Cypher Manual -> Vector indexes].

Then you need to add a prompt that contains a detailed use-case or context, a description of what you want the agent to be able to do, and any other preferences.
The more details you provide, the more accurate the generation will be.
Once you are satisified, use *Create* to start generating your agent.

When the agent has been created you should test it to make sure it behaves as expected.
See <<test-agent>> for guidance and the <<tools>> section for more information on available tools.

If you are not happy with the agent, you can iterate on the agent manually or you can regenerate it by editing the prompt via the *Regenerate with AI* button.
Note that this action *overwrites* the current configuration.

Once you are satisfied with your agent, use *Create agent* to persist it.


[[tools]]
== Tools

Aura Agent has three tools available:

* *Cypher Template*
* *Similarity Search*
* *Text2Cypher*

Consider your dataset and its underlying data model when you configure the tools to ensure your agent has access to the right ways of retrieving *only* the right information.

=== Cypher Template

This tool executes pre-defined, parameterized Cypher queries against the database and returns the results to the agent.
The values for the parameters are provided by the user.
It works in the same way as other Cypher queries you write but is reusable by the agent.

This tool is best for:

* Common and repeated questions
* Predictable results
* Complex queries
* Well-defined business logic patterns

You need to provide a *name* and a *description* for the tool.
The better the description, the better your agent will perform.
If your query contains *parameters*, they need to be defined with a *name*, *data type*, and *description*.

[.shadow]
.Cypher Template tool
image::cypher-template.jpg[width=400]

For best performance, make sure that the query:

* Returns only relevant information
* Returns only select node and relationship properties
* Does not return embeddings or graph elements like nodes, relationships, or paths.
* Does not return duplicates

Additionally, it is advisable to limit the results to 10-50 rows to keep the results relevant.
Also, always test the Cypher statement to make sure it works as expected.

[[similarity-search]]
=== Similarity Search

This tool uses vector similarity to do a semantic search.
The similarity search finds the semantically similar entities and the Cypher template can find connections between these, which provides relevant context for the agent.

This tool is best for:

* Document search
* Content discovery
* Finding similar clauses or terms
* Semantic matching

Note that the similarity search requires *text embeddings* and the presence of a *vector index* in your database.
Aura Agent currently supports embeddings generated with the following text embedding providers and models:

* OpenAI (via Azure OpenAI): `text-embedding-3-small`, `text-embedding-3-large`, and `text-embedding-ada-002`.

* Vertex AI: `gemini-embedding-001`, `text-embedding-005`, and `text-multi-lingual-embedding-00`.

For more information about vectors and embeddings, see the link:{neo4j-docs-base-uri}/cypher-manual/current/indexes/semantic-indexes/vector-indexes/#embeddings[Cypher Manual -> Vectors and embeddings in Neo4j] and link:{neo4j-docs-base-uri}/cypher-manual/current/indexes/semantic-indexes/vector-indexes/[Cypher Manual -> Vector indexes].

You need to provide the name of your vector index and a value for *Top K*, i.e. the number of results you want the search to return.

To further process the similarity search results, check *Return connected graph data*.
This lets you write a Cypher query that is appended to the vector search and runs as a single query, with `node` (the matched node) and `score` (the similarity score) already in scope.

You can write the query directly in the *Cypher* tab, or describe the traversal, i.e. what the query should accomplish, in the *Natural language* tab and use *Generate* to produce a Cypher query.
Review and optionally edit the query in the *Cypher* tab and use *Add tool* to save it.
Note that the natural language description is not saved, only the final Cypher query is stored with the tool.

You can add multiple similarity search tools with the same vector index but with different post-processing queries to cover different traversal patterns.

[TIP]
====
Use the *Similarity Search* tool when your starting point is a vector index.
Use the *Cypher Template* tool for arbitrary read queries that do not require a vector lookup.
====


[.shadow]
.Similarity search tool
image::similarity-search.jpg[width=400]

[NOTE]
====
Aura Agent performs vector similarity search using the same embedding model used to generate your stored embeddings.
This ensures aligned vector spaces.
For more information on Aura Agent and AI models, see link:{neo4j-docs-base-uri}/reference/license/agent-ai-model/[License and disclaimers -> How Aura Agent uses AI models].
====

=== Text2Cypher

This tool transforms natural language questions into Cypher queries and allows the agent to retrieve data dynamically.
In essence, the tool takes the question, adds the database schema and the Text2Cypher system prompt to it, and presents these to a fine-tuned model.
The model then generates a Cypher query for the tool to execute.

[CAUTION]
====
The Text2Cypher tool relies on an LLM and this can potentially result in queries that contain inconsistencies or logical errors.
Therefore, use caution when deploying Text2Cypher in production.
====

The Text2Cypher tool is best for:

* Questions that can't be predicted in advance
* Structural queries like aggregations

[.shadow]
.Text2Cypher tool
image::text2cypher.jpg[width=400]

You need to give the tool a name and a description.
To improve reliability of its answers, it is important that both name and description are as clear as possible to constrain the tool's usage.

The instructions should include:

* When to use the Text2Cypher tool (and when not)
* Specific aspects about your database and domain
* Relevant entities and especially information about searchable categorical properties, e.g. shape of identifiers.
* Which attributes are suitable for aggregation

As a best practice, this tool should only be used when none of the other tools meet your needs, so make sure the description explicitly instructs the agent to use this tool only when no other option applies.

[[test-agent]]
== Test the agent

Before you make your agent public or share it with internal users, you can test it to make sure it works as intended.
Once you are satisfied with your tools, you can start asking your agents questions.

To verify that your agent operates the way you want, ask it a question, and once it responds, use the dropdown to see how it reasons.

The agent tells you how it interpreted the prompt and which tool(s) it used.
If more than one tool was used, the agent shows the first tool, its input and its output, and then what the next step was and then the process is iterated until the agent had collected enough information to return an answer.

This way, the reasoning is transparent and if your agent is not acting to your expectations, consider changing the tool descriptions to make sure the right tool is used in the right situation.

Save your agent once you are happy with it.
A saved agent can then be used internally, i.e. by other users in your Aura project, but only project admins can create, edit, or delete agents.

[[agent-evaluation]]
== Agent evaluation

A structured evaluation tests whether the agent behaves the way you expect.
An evaluation asks your agent a fixed set of test questions and scores each answer against an expected answer and, optionally, the tools it was expected to call.

Use agent evaluation before you promote an agent to production, after you change its prompt or tools, or whenever you want to check for regressions before relying on an agent's answers again.

You can access agent evaluation from the *[...]* menu next to an agent, using *Agent evaluation*.

=== Evaluation datasets

An evaluation dataset is a named set of test questions you run an agent against.
Each question has the question text itself, an expected answer, and, optionally, one or more expected tool calls, i.e. which tool you expect the agent to use and with what input.

An evaluation dataset belongs to your Aura project, not to a single agent, so you can reuse the same dataset to evaluate several agents, for example when comparing two versions of an agent built against the same knowledge graph.

==== Create an evaluation dataset

You can create a dataset in two places:

* While setting up an evaluation, using *Create new dataset*.
* From the *Evaluation datasets* page, using the *Create new dataset* button.

Both lead to the same authoring screen.
Give the dataset a name and, for each test question, provide the question text and the expected answer.
If you want the evaluation to also check tool usage for that question, add one or more expected tool calls.
Specify the tool's name and the input you expect the agent to pass to it.

An evaluation dataset can hold up to 50 questions.

[TIP]
====
If you use an LLM to help you draft an evaluation dataset, give it your agent's exported JSON definition (see <<import-export-agent>>) alongside your prompt, not just a description of the use case.
Expected tool calls have to match the tools your agent actually has, with their real names and input shapes.
An LLM working from a general description alone tends to invent tool calls that look plausible but don't match what your agent can call.
====

==== Manage an evaluation dataset

The *Evaluation datasets* page lists every dataset in your project, with its description, question count, and when it was last updated.
Select a dataset to show its questions.

You can edit a dataset's name and description at any time.
The questions are permanently read-only once a dataset is saved.
Changing a question after it has been used in an evaluation would change what that evaluation's scores actually mean.
If you need to edit the questions, use *Create from this* from the *[...]* on the dataset to start a new, separate dataset seeded with a copy of the same name, description, and questions.
The copy is independent from the moment it's created: editing or deleting one dataset never affects the other.

There is no dataset version history, so editing a dataset's name or description changes that one copy going forward, it doesn't keep older copies around.

==== Delete an evaluation dataset

Deleting a dataset also deletes the evaluation history of every evaluation that used it, and this cannot be undone.
If an evaluation using the dataset is still queued or in progress, you can't delete the dataset until that evaluation finishes.

=== Run an evaluation

*Run evaluation* has two tabs.

* *Dataset*: pick an existing dataset or create a new one, as described above.
* *Metrics*: select which metrics to score this evaluation on.

*Latency* is always measured and can't be turned off.
The other metrics, *Accuracy*, *Relevance*, *Grounding*, and *Tool trajectory*, are opt-in checkboxes; select any combination of them for the evaluation.
See <<agent-evaluation-metrics>> for more information on each metric.

Once you start the evaluation with *Run evaluation*, it executes in the background.
You can navigate away from the page, and the evaluation keeps going.
An evaluation moves through these statuses: *Queued*, *Running*, and then one of *Succeeded*, *Failed*, or *Cancelled*.
If you have an agent evaluation page open when an evaluation finishes, you get a notification with a link straight to its results.

You can cancel an evaluation while it's still queued or running, from its row menu on the evaluation history page.
Confirm the cancellation, and the evaluation stops after the question it's currently on finishes, so its progress may still tick up briefly right after you cancel.
A cancelled evaluation keeps whatever results it collected before you stopped it.

=== Evaluation history

The evaluation history page lists every evaluation for this agent: when it ran, its status, which dataset it used, its progress, and its average score for each metric it was run with.
Open any row to see that evaluation's full results.

To evaluate the agent again with the same dataset and metrics, use *Run again* from a past evaluation's row menu or from its results page.

=== Reading an evaluation's results

If you open an evaluation from the evaluation history page you can view its results, with two tabs: *Overview* and *Questions*.

*Overview* shows the total number of questions, how long the evaluation took, the average latency, and one average score card for each metric you selected for the evaluation.
If the evaluation has a metric averaging below the warning threshold, you also see a short insight card naming the worst-performing metric, so you know where to look first.
If the evaluation itself failed, was cancelled, or had failing questions, you instead see a status banner describing that instead of the insight card.

*Questions* lists every question in the evaluation, with its test question, expected answer, the agent's actual answer, the expected tools, its latency, and a column for each metric you selected.
Open a question to see its full detail, including the expected and actual tool calls side by side, each with the input it was called with.
When the agent's tool call returned a result, you can expand an *Output* section to see the raw result the tool returned.
In the question detail view, you can also switch the agent's answer between rendered and raw text; the table itself always shows the rendered version.
Hover over a metric's score to see the reason behind it.

A question that failed, for example because the agent or a tool errored, is flagged differently from a question that simply scored low.
A low score is still a real answer you can learn from; a failure means the question wasn't meaningfully evaluated at all, so the two need different follow-up.

[[agent-evaluation-metrics]]
=== Metrics

Each metric answers a different question about the agent's answer, and is graded differently.

*Accuracy* (`LLM judge`, scored 0 to 1) asks whether the answer is factually correct and complete compared to the expected answer.
Wording, formatting, or extra correct detail don't affect the score, only the substance does.
A claim in the answer that isn't backed by the expected answer counts against it as an unsupported claim, even if the rest of the answer is right.
Accuracy is graded by a judge LLM, which *compares the agent's answer against the expected answer* and returns a score with a written reason.

*Relevance* (`LLM judge`, scored 0 to 1) asks a narrower question than Accuracy: does the answer actually address what was asked, regardless of whether it's factually correct.
A confident answer that's wrong but stays on topic still scores well on Relevance, even though it scores poorly on Accuracy; conversely, a correct fact that doesn't answer the question asked scores poorly on Relevance even though it might be accurate on its own.
Relevance is graded by a judge LLM, working *from the question and the agent's answer alone*, without comparing against the expected answer.

*Grounding* (`LLM judge`, scored 0 to 1) asks a different question again: whether *the answer is actually supported by what the agent's own tools returned, regardless of whether the answer is correct*.
An answer that faithfully reports what the tools said is well grounded even if the tools themselves were wrong; an answer with claims the tools never supported is poorly grounded even if the claim happens to be true.
Grounding is also graded by a judge LLM, given the tool results as evidence.
When the agent didn't call any tools for a question, there's no evidence to check the answer against, so grounding shows as not applicable rather than a score.

*Tool trajectory* (`Deterministic` + `LLM judge`, shown as a percentage) *compares the tools the agent actually called, with their inputs, against the tools the question expected*.
The score is a Jaccard similarity: the share of expected and actual calls that match, out of every call on either side, so missing an expected call or making an extra unexpected one both pull the score down.
The order the tools were called in doesn't matter, and calling the same tool more than once is expected to match a duplicate expected call.
Matching is exact for a Cypher Template call: its parameters have to match precisely to count.
Text2Cypher and Similarity Search calls take a natural-language query instead of a fixed parameter, so an exact match is the exception, not the rule.
When one isn't found, a judge LLM decides whether a differently worded query asks for the same thing, and counts it as a match if so.
Since agents lean on Text2Cypher and Similarity Search often, this judge LLM step is a routine part of scoring most trajectories, not a rare fallback.

*Latency* is the wall-clock time the agent took to produce its complete answer for that question.

Accuracy, Relevance, Grounding, and Tool trajectory all show a warning indicator when a question scores below 0.8.
This is a fixed line the product uses to flag a score worth a closer look, not a pass or fail grade, and not a value calculated from your data.
A score of 0.79 isn't meaningfully different from 0.81, it's simply on the other side of where the UI draws attention.

There's no confidence or probability interval behind any of these scores.
Accuracy, Relevance, and Grounding each come from a single judge LLM judgment, with its reasoning shown as a tooltip on the score.
Tool trajectory comes from directly comparing the calls themselves, deterministically, plus a judge LLM to decide whether two differently worded Text2Cypher or Similarity Search queries mean the same thing, which for many agents is the more common path.

=== Example

The following is a trimmed excerpt of a real agent and evaluation dataset, to show the shapes described above in context.
The agent below has three tools: two Cypher Template tools and a Text2Cypher tool.
This is the same JSON format produced by <<import-export-agent>>.

[source,json]
----
{

  "description": "A versatile assistant for querying movies and the people involved in them, including actors, directors, producers, writers, and reviewers. It can provide detailed movie overviews, actor filmographies, and social connections between people.",
  "system_prompt": "You are a helpful assistant for querying information about movies and people in a graph database. Provide clear and concise answers based on the available data. When a movie or person name is provided, assume it's an exact match.",
  "is_private": false,
  "is_mcp_enabled": false,
  "tools": [
    {
      "name": "Movies by Actor",
      "description": "Lists all movies an actor has appeared in, along with their roles in those movies, ordered by release year.",
      "enabled": true,
      "type": "cypherTemplate",
      "config": {
        "template": "MATCH (p:Person {name: $actorName})-[r:ACTED_IN]->(m:Movie) RETURN m.title AS movieTitle, m.released AS releasedYear, r.roles AS roles ORDER BY m.released DESC LIMIT 25",
        "parameters": [
          {
            "name": "actorName",
            "data_type": "string",
            "description": "The exact name of the actor."
          }
        ]
      }
    },
    {
      "name": "Movie Directors",
      "description": "Finds the names of all directors for a specified movie.",
      "enabled": true,
      "type": "cypherTemplate",
      "config": {
        "template": "MATCH (m:Movie {title: $movieTitle})<-[:DIRECTED]-(p:Person) RETURN p.name AS directorName ORDER BY directorName LIMIT 10",
        "parameters": [
          {
            "name": "movieTitle",
            "data_type": "string",
            "description": "The exact title of the movie."
          }
        ]
      }
    },
    {
      "name": "Natural Language to Cypher Tool",
      "description": "A general-purpose, free-form Text-to-Cypher tool that converts natural language questions into Cypher queries, executes them, and returns the results. Use this option when no specialized tool (e.g. for aggregation or domain-specific logic) is more appropriate.",
      "enabled": true,
      "type": "text2cypher"
    }
  ]
}
----

A dataset built for this agent gives each question an expected answer, and, for questions that should use a tool, the exact tool name and input to expect.

Notice how the two Cypher Template questions expect a specific parameter value, while the Text2Cypher questions expect a natural-language `query`.

== Make your agent public

There are two different ways to interact with your agent externally.
You can integrate your agent into your GenAI application by making it publicly available via REST API from an endpoint, or you can make it available to an MCP client via an MCP server endpoint.

[NOTE]
====
Once you make your agent public, it starts to incur charges.
See link:https://console.neo4j.io/pricing[Neo4j pricing] for more information.
You can change an agent's availability at any time.
====

=== REST API

Use *Configure* to edit your agent from the *[...]* menu, and select *External* access.
Once you *Update agent*, the endpoint can be copied from the same *[...]* menu.

[.shadow]
.Copy endpoint from *[...]* menu
image::agent-endpoint.jpg[width=400]

To access the endpoint externally, you need to have an xref:api/authentication.adoc#_creating_credentials[Aura API key] to generate a client ID and secret.

Once you have these, verify them in the terminal:

[source,shell]
----
export CLIENT_ID=<enter your Client ID here>
export CLIENT_SECRET=<enter your Client Secret here>
export ENDPOINT_URL=<enter your agent endpoint URL>
----

The next step is to obtain a bearer token:

[source,shell]
----
export BEARER_TOKEN=$(curl -s --request POST 'https://api.neo4j.io/oauth/token' \
    --user "$CLIENT_ID:$CLIENT_SECRET" \
    --header 'Content-Type: application/x-www-form-urlencoded' \
    --data-urlencode 'grant_type=client_credentials' | jq -r .access_token)
----

Then use the bearer token to ask your agent a question:

[source,shell]
----
url --request POST "$ENDPOINT_URL" \
 -H 'Content-Type: application/json' \
 -H 'Accept: application/json' \
 -H "Authorization: Bearer $BEARER_TOKEN" \
 -d '{"input": "<YOUR AGENT QUESTION>"}' \
 --max-time 60 | jq .
----

The agent's response is returned as a structured JSON message.

Note that this example uses link:https://jqlang.org/[jq] for command line JSON processing.

=== MCP server

The other option is to make your agent available to an MCP client such as Claude Desktop, VSCode MCP, or Microsoft Copilot Studio.
In this setup, your agent acts as an read-only MCP server that allows an external agent to use your agent and its target instance as a tool to answer inquiries.

Once you are satisfied with your agent, make it *external* and *enable MCP server* before saving it.

[.shadow]
.Make the agent external and enable MCP-server
image::enable-mcp.jpg[width=300]

Next you need to copy the MCP server endpoint.
It can be found from the *[...]* menu on the agent.

[.shadow]
.Copy MCP server endpoint from *[...]* menu
image::agent-endpoint.jpg[width=400]

Then you go to your MCP client of choice and add a remote MCP entry with the MCP server endpoint for your agent.
You may need to restart the client after.

Once your MCP server has been attached to the client, you need to authorize it to access your account.
Two different authorization flows are supported:

* *User* (authorization code): Use the same credentials you use to log in to the Aura console.
You may need to enable the newly added MCP server in the client before the client can invoke it.

* *Machine-to-machine* (client credentials): Service-to-service access using credentials issued by the Aura console.

==== Machine-to-machine authorization flow

When calling the agent MCP server from a script or service, use the following flow:

. Create credentials
+
* Go to your profile menu from the top right corner in the console
* Select *Account settings*
* Select the *Client credentials* tab and *Aura Agent & MCP*
* Use the *Create client credential* button and enter a name and use the dropdown to choose what this client credential can be used to access
* Confirm with *Create*
* Store the generated credentials somewhere secure, either copy them or use the *Download and close* button.
+
. Exchange for an access token
+
In the MCP client application, use the client credentials to request an access token:
Post a `client_credentials` grant to the gateway token endpoint:
+
[source, shell]
----
POST https://mcp.neo4j.io/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=<ClientId>
&client_secret=<ClientSecret>
&audience=https://agent-mcp.neo4j.io
----
+
Note that the endpoint is rate-limited to 15 requests per hour per `client_id`.
To avoid exceeding this quota, cache the returned `access_token` for its full `expires_in` window instead of requesting a new token for every request.
+
. Call the agent
+
Use the JWT as a bearer token on `Post /agent`:
+
[source, shell]
----
POST https://mcp.neo4j.io/agent?project_id=<project_id>&agent_id=<agent_id>
Authorization: Bearer <access_token>
----

==== Set up with Microsoft Copilot Studio

Start by making your agent public and enable MCP server, as described above, and copy the MCP server endpoint accordingly.

Your MCP endpoint URL contains `project_id` and `agent_id` as query parameters. These pieces of information are *crucial* for the MCP server endpoint to be able to *identify* your project and agent.

Note that Copilot Studio's Streamable HTTP runtime *strips all query parameters* from outgoing requests.
*Therefore, make sure to note the two values from the query string before proceeding.*
You will need them later to add as headers to requests made from Copilot Studio.

. Add the MCP server in Copilot Studio
+
In link:https://copilotstudio.microsoft.com[Copilot Studio], open your agent and go to *Tools* > *Add a tool* > *Add an MCP server*.
Enter the *MCP endpoint URL* and follow the wizard to connect.
+
For authentication choose *OAuth 2.0* > *Dynamic Discovery*.
Authenticate with the same credentials you use to log in to the Aura Console.
+
Copilot Studio creates a Power Apps custom connector in the background.
+

. Edit the custom connector in Power Apps
+
Sign in to link:https://make.powerapps.com[Power Apps].
From the left navigation, select *Data* > *Custom connectors* and find the connector that Copilot Studio just created.
(You may need to go to *More* > *Discover all* to find the *Custom connectors* menu.)
Open it for editing and enable *Swagger editor*.

. Add internal header parameters
+
In the Swagger editor, locate the `parameters` array inside the `/agent` POST action and add the `project-id` and `agent-id` header entries, replacing the placeholder values with your actual `project_id` and `agent_id` from the first step.
+
Setting `x-ms-visibility: internal` hides these parameters from end users while Copilot Studio sends them silently as request headers.
Note that the parameter names use hyphens (`project-id`, `agent-id`), not underscores.
+
The result should look similar to the following:
+
[source,yaml]
----
swagger: '2.0'
info:
  title: My Movie Database MCP Server Connection
  description: Get information on movies, actors and directors
  version: 1.0.0
host: mcp.neo4j.io
basePath: /
schemes:
  - https
paths:
  /agent:
    post:
      responses:
        '200':
          description: Immediate Response
      x-ms-agentic-protocol: mcp-streamable-1.0
      operationId: InvokeServer
      summary: My Movie Database MCP Server Connection
      description: Get information on movies, actors and directors
      parameters:
        - name: project-id
          in: header
          required: true
          type: string
          description: The specific project ID context
          default: <project_id>
          x-ms-visibility: internal
        - name: agent-id
          in: header
          required: true
          type: string
          description: The executing agent context
          default: <agent_id>
          x-ms-visibility: internal
securityDefinitions: {}
security: []
----

. Save and verify
+
Use *Update connector* to save your changes.
In Copilot Studio, open the test playground and ask your agent a question that exercises the Aura Agent tools to verify the connection is working end-to-end.

== Import/Export agent

Existing agents can be exported in as _JSON_ format.
You can either download the _JSON_ file or copy it to the clipboard.
This is done from the *[...]* menu on the agent.

[.shadow]
.Export an agent as _JSON_
image::export-agent.jpg[width=400]

If you have a _JSON_ file of an agent, you can use that to create a new agent.
Use the *Import agent* button and select the instance the new agent should target.
Then you can either browse for or paste the configuration for the agent.

You can edit the _JSON_ file, such as change the name of the agent, for example.
However, keep in mind that *internal* (`"is_private": true`) agents *cannot* be enabled as MCP server (`"is_mcp_enabled": true`).
