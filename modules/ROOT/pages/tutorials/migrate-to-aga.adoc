= Migrate to Aura Graph Analytics

This tutorial describes how to migrate existing graph data science workloads to Aura Graph Analytics (AGA) from AuraDS or AuraDB Graph Analytics plugin.

== Architecture changes

The main difference when migrating to AGA is the shift from a persistent compute model to an on-demand (ephemeral) session model.

[cols="1s,2a,2a"]
|===
|| AuraDS / Graph Analytics plugin| Aura Graph Analytics

|Compute resource
|Always-on instance (AuraDS) +
Shared DB resources (plugin)
|Sessions created on-demand for the duration of the task

|Data location
|Data resides on the same machine as the compute
|Data is loaded from your source (Neo4j DB or external) into the session's memory

|Authentication
|Database credentials
|Implicit (from the Aura Console) or Aura API credentials (for external usage and scripts)

|Cost model
|Flat hourly rate (AuraDS) +
Included in the instance cost (plugin)
|Pay-as-you-go (billed only while the session is active)
|===

== Phase 1: Authentication and prerequisites

Unlike standard Neo4j connections, Aura Graph Analytics requires authentication to the Compute Layer (to spin up sessions) separate from the Data Layer (to read your graph).

How you handle this depends on where you run your code:

=== Scenario A: Running in Aura Console (Simplest)

Use this for quick exploration via the "Query" tab within Aura.
No setup required.
Because you are already logged into the Aura Console, you are implicitly authorized to create analytics sessions. You do not need to generate or provide Aura API keys.

Action: You can skip directly to running Cypher.

[source]
// Works immediately without credentials
CALL gds.graph.project(..., { memory: '8GB' })

=== Scenario B: Running Python or external scripts

Use this for notebooks, scheduled jobs, or any script running outside the Aura Console.
You must explicitly authenticate with the Aura API to authorize the creation of compute resources.

* Generate Credentials:
Navigate to the API Keys page (Organization Level).
Generate a client_id and client_secret.
Note: Save the secret immediately; it cannot be viewed again.

* Update Your Code Accordingly (optional):
Update your scripts or application configuration to retrieve and use these new client_id and client_secret values instead of your database username and password.

Important: Two Layers of Authentication (For Python/External Users)

* Layer 1 (Compute): Aura API credentials unlock the ability to spin up the ephemeral compute session.
* Layer 2 (Data): If you're loading data from AuraDB or self-managed Neo4j, your standard database username/password unlocks the ability to read your specific graph data.

== Phase 2: Python client migration

If you use the graphdatascience Python library, you must update how you instantiate the GDS object and how you project graphs.

=== 1. Connecting to the instance

[.tabbed-example]
====
[.include-with-AuraDS-or-plugin]
=====
You connected directly to a specific database URI.

[source, python, subs=attributes+]
----
from graphdatascience import GraphDataScience

# Direct connection to the database/instance
gds = GraphDataScience(
    "neo4j+s://my-aurads-instance.databases.neo4j.io", 
    auth=("neo4j", "password")
)
----
=====

[.include-with-Aura-Graph-Analytics]
=====
You use the GdsSessions class to authenticate with the Aura API and spawn a session.

[source, python, subs=attributes+]
----
from graphdatascience.session import GdsSessions, AuraAPICredentials, SessionMemory, DbmsConnectionInfo

# 1. Authenticate with Aura API
sessions = GdsSessions(
    api_credentials=AuraAPICredentials(
        client_id="<YOUR_CLIENT_ID>",
        client_secret="<YOUR_CLIENT_SECRET>",
        project_id="<YOUR_PROJECT_ID>" # Optional if you have only one project
    )
)

# 2. Define the source database (if loading from AuraDB)
db_connection = DbmsConnectionInfo(
    aura_instance_id="<YOUR_INSTANCE_ID>",
    username="neo4j",
    password="<YOUR_PASSWORD>"
)

# 3. Get or create the session
# This returns a 'gds' object configured to run on the remote session
gds = sessions.get_or_create(
    session_name="my-analytics-job",
    memory=SessionMemory.m_16GB,
    db_connection=db_connection
)

# Now 'gds' works exactly like it did before, but runs on the session
----
=====
====

Tip box: You can verify that the connection is correctly configured via the gds.verify_connectivity() utility function.

=== 2. Projecting the graph

Because the compute (AGA) is separate from the storage (AuraDB), you cannot use standard "Native Projections." You must use a Remote Projection to pull data over the network.

[.tabbed-example]
====
[.include-with-AuraDS-or-plugin]
=====
[source, python, subs=attributes+]
----
G = gds.graph.project("my-graph", "Person", "KNOWS")
----
=====

[.include-with-Aura-Graph-Analytics]
=====
Path A: From AuraDB or Self-Managed Neo4j (Remote Projection)

If the session reads data from a Neo4j source, you must use gds.graph.project with a query that specifically calls gds.graph.project.remote. This special procedure moves data from the source DB to the session.

[source, python, subs=attributes+]
----
# The query runs on your DB, but projects into the session
query = """
    CALL gds.graph.project.remote(
      $graph_name,
      'MATCH (n:Person) RETURN n',
      'MATCH (n:Person)-[r:KNOWS]->(m:Person) RETURN n, r, m'
    )
"""

G, result = gds.graph.project(
    graph_name="my-graph",
    query=query
)
----

Path B: From DataFrames (Standalone)

If your data comes from a non-Neo4j source (via Pandas DataFrames), there is no connected database to run Cypher against. In this case, you use `gds.graph.construct` to load data directly from memory structures.

[source, python, subs=attributes+]
----
# 1. Prepare your DataFrames (Example)
nodes = pandas.DataFrame({
    "nodeId": [1, 2, 3],
    "labels": ["Person", "Person", "Person"],
    "age": [25, 30, 35]
})

rels = pandas.DataFrame({
    "sourceNodeId": [1, 2],
    "targetNodeId": [2, 3],
    "relationshipType": ["KNOWS", "KNOWS"]
})

# 2. Construct the graph in the session
G = gds.graph.construct(
    "my-dataframe-graph", 
    nodes, 
    rels
)
----
=====
====


Note: `gds.graph.construct` is highly efficient for data pipelines (e.g., Airflow) where data is already being processed in Python/Pandas before being sent to Aura Graph Analytics.

== Phase 3: Cypher migration
If you are running GDS algorithms directly via Cypher (e.g., in Aura Console or Neo4j Browser), the syntax depends on your environment and permission level.

[.tabbed-example]
====
[.include-with-AuraDS-or-plugin]
=====
[source, cypher, subs=attributes+]
----
CALL gds.graph.project('my-graph', 'Person', 'KNOWS');
CALL gds.pageRank.stream('my-graph') YIELD nodeId, score;
----
=====

[.include-with-Aura-Graph-Analytics]
=====
By default, when you are logged into an AuraDB instance, you are automatically authorized to create and manage your own analytics sessions. You do not need to handle API credentials manually.
How to migrate:
Simply add a configuration map with a memory key to your projection call. This triggers the remote session creation.

[source, cypher, subs=attributes+]
----
// 1. Project and Create Session
// The {memory: '8GB'} configuration automatically triggers the remote session
CALL gds.graph.project(
  'my-graph',       
  'Person',
  'KNOWS',
  {},               // (Optional) Node/Rel Properties config               
  { memory: '8GB', ttl: duration({hours: 1}) } // <--- Session config 
);
// 2. Run algorithms normally
// The system knows 'my-graph' lives in the remote session
CALL gds.pageRank.stream('my-graph') 
YIELD nodeId, score;

// 3. Drop the graph to stop the session (stopping costs)
CALL gds.graph.drop('my-graph');
----
=====
====

== Key operational differences and constraints

Essential platform behaviors legacy users must be aware of.

=== Maximum session duration (hard stop)

Unlike AuraDS instances which run indefinitely, Aura Graph Analytics sessions have a hard limit of 7 days (168 hours).
Behavior: The session will automatically terminate after this period, regardless of whether a job is currently running.
Impact: Long-running workflows must be designed to complete within this window or checkpoint results externally.

=== File system access and exporting

Because the session is a stateless compute resource, you cannot access the server's local file system directly.
Behavior: Server-side export procedures (like CALL gds.graph.export.csv) attempt to write to the server's disk. These are not supported and will fail in both Cypher and Python.
Alternative: You must stream the results back to the client first.
Python: Stream the graph or properties into a Pandas DataFrame (e.g., gds.graph.nodeProperties.stream), then use df.to_csv() to save it to your local disk.

=== Session startup latency (cold start)

Creating a new session involves provisioning isolated compute infrastructure on demand.
Behavior: This process is not instantaneous and can take from a few seconds to a few minutes.
Impact: Do not embed session creation inside synchronous, latency-sensitive user requests (e.g., a web API call). Pre-warm sessions or use asynchronous job queues.

=== Organization limits

Your organization has configurable quotas that cap both the number of simultaneous sessions and the maximum memory size of any single session.

Behavior:
Concurrency: If you attempt to spawn more sessions than allowed (e.g., during a parallel batch job), you will receive a Session limit reached error.
Size: If you attempt to create a session larger than your organization's max allowed size (e.g., requesting 256GB when the limit is 64GB), the request will be rejected.
Impact: Verify that your organization's quotas are aligned with your workload requirements before deployment. You may need to request a quota increase if your use case requires massive scale or high concurrency.

=== Potential cloud provider data transfer costs (egress)

Behavior: Loading data from an AuraDB instance in the same region is efficient and typically free. However, loading data across regions or from an external cloud provider involves data movement.
Impact: This may incur data egress fees from your cloud provider. Where possible, co-locate your session in the same region as your data source.

== Best practices

=== Right-sizing memory

In AuraDS, you paid for a fixed instance size (e.g., 64GB). In AGA, you can choose the exact memory needed for each specific job. To avoid guessing or hitting Out-Of-Memory (OOM) errors, use the estimation utility before creating your session.

Python Client: The sessions object has a built-in estimator that calculates the required memory based on your expected data volume.

Cypher: Cypher doesn't have a built-in estimation function, so we recommend starting with your best estimate based on your understanding of the dataset. If you encounter Out-Of-Memory (OOM) errors, increase the memory parameter.
Note box: Use the estimation utility to get a baseline, but treat it as a starting point rather than a guarantee.

=== Manage TTL (Time-To-Live)

Always set a TTL for your sessions to prevent accidental costs if a script crashes before it can tear down the session.

Python: gds.get_or_create_session(..., ttl="1h")

=== Model persistence

Current Limitation: Trained Machine Learning models (e.g., Link Prediction, Node Classification) live only as long as the session.

Workaround: If you need to re-use a model later, you must re-train it in the new session. We are actively working on model persistence capabilities.
